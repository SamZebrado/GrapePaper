## 正文

### 1. 摘要

做了一个叫 **GrapePaper** 的学术编辑器原型——段落渲染为石板、批注像葡萄叶生长、引用如露水闪烁、AI 对话以泡泡形式浮现。用 TRAE SOLO 完成了从竞品调研、架构设计到代码开发、测试覆盖的全流程。项目使用 React + TypeScript + Vite 构建，包含 9 个核心组件、60 个测试用例、支持 Markdown/JSON 导入导出和 localStorage 持久化。

### 2. 背景

我是一名博士生，日常需要大量阅读和撰写学术论文。虽然不是职业开发者，但科研工作中经常需要写代码、搭工具，积累了比较丰富的业余开发经验。传统的论文编辑器（Word、Overleaf、Google Docs）界面千篇一律——白底黑字、线性排版。对需要长时间面对屏幕的写作者来说，视觉疲劳和心理压力是真实存在的问题。

我想探索一个方向：**如果论文编辑器不长得像论文，而长得像一个花园呢？**

这个想法酝酿了挺久。对规整论文产生厌恶其实不一定是规整论文本身的问题，但至少可以给情绪一个平稳的"台阶"，让人有更多勇气坐下来写东西。

### 3. 实践过程

#### 第一步：竞品调研

首先让 SOLO 对"视觉隐喻型论文编辑器"做了一轮竞品调研，覆盖了 Gingko Writer、Scrintal、Heptabase、LiquidText、Curvenote、Hypothesis 等产品。

结论是：**直接竞品很少**——没有人在做"葡萄藤/石板/露水"这种强视觉隐喻的论文编辑器。但相邻竞品不少，Gingko Writer 主打 ADHD 友好的树状写作，Scrintal 做 PDF + 笔记 + infinite canvas，Heptabase 做可视化知识库，LiquidText 做跨文档批注连接，Curvenote 做科学写作，Hypothesis 做社交标注。

所以 GrapePaper 的定位不是"功能首创"，而是**用一个很强的自然隐喻渲染层，把写作、批注、引文、AI 对话整合到同一体验里**。

#### 第二步：架构设计与技术选型

确定了技术栈：
- **React 18 + TypeScript 5.6 + Vite 6**（从 Vite 8 降级，解决 Rolldown 跨平台问题）
- **Zustand** 状态管理
- **TipTap** 富文本编辑（基于 ProseMirror）
- **Framer Motion** 动画
- **CSS Modules + CSS Variables** 主题系统

#### 第三步：核心组件开发

让 SOLO 一次性生成了 9 个核心组件：

| 组件 | 视觉隐喻 | 功能 |
|------|----------|------|
| StoneSlab | 🪨 石板 | 段落编辑器，多层 CSS 渐变模拟石头纹理 |
| GrapeLeaf | 🍇 葡萄叶 | 批注展示，CSS clip-path 叶形 + 弹性动画 |
| DewdropCitation | 💧 露水 | 引用高亮，悬浮显示作者/标题/摘要 |
| ChatBubble | 💬 泡泡 | AI 对话，古老消息自动缩小 |
| ChatPanel | 📋 面板 | 右侧滑出聊天面板 |
| VineConnector | 🌿 藤蔓 | SVG 贝塞尔曲线连接段落 |
| Sidebar | 📑 侧栏 | 文档导航和标题编辑 |
| EditorCanvas | 🖼️ 画布 | 主编辑区域 |

#### 第四步：迭代与修复

开发过程中遇到了几个关键问题，多次迭代才解决：

**踩坑 1：Vite 8 + Rolldown 跨平台失败**
- 现象：`Cannot find native binding @rolldown/binding-darwin-arm64`
- 一位很有用的 LLM 帮我分析后指出：Vite 8 切到了 Rolldown 作为统一 bundler，对 Node 版本和平台有严格要求，而 npm 的 optional dependency 机制在跨机器传播时可能静默缺包
- 解决：降级到 Vite 6（esbuild），同时调整 React 19→18、TypeScript 6→5.6 等依赖版本

**踩坑 2：工程交付质量不足**
- 第一版交付物带了 `node_modules`、`dist`、`.git`，`README.md` 还是默认 Vite 模板，`package.json` 名字还叫 `grapepaper-temp`
- 上述 LLM 指出：应该先修可运行性和文档诚实度，再继续堆功能
- 解决：清理交付物、修正元信息、重写文档、诚实标注 mock/未实现功能

**踩坑 3：UI 状态管理混乱**
- Toast 和 Confirm 组件通过 `window` 全局暴露，不够优雅
- 解决：重构为 React Context + `useUI()` hook，统一 UI 状态管理

#### 第五步：功能完善

经过多轮迭代，逐步添加了：
- localStorage 持久化（刷新不丢数据）
- Markdown / JSON 导入导出
- Annotation 编辑和删除
- 60 个单元测试（Vitest + Testing Library）
- Toast 通知和 Confirm 模态框

### 5. 效果与总结

**SOLO 在这个项目里扮演了什么角色？**

用一句话概括：**SOLO 更像"高速度施工队"，不是"自动总包监理"。**

它是一个高吞吐、可反复指挥的实现代理 + 重构执行器 + 文档/测试补全器。具体来说：

**它真正承担掉的工作：**
- 把想法迅速落成代码（9 个组件一次生成，从想法到可运行原型非常快）
- 高频、机械、容易烦的重构（版本统一、导入导出逻辑抽取、alert/confirm 改成统一 UI）
- 大批量样板代码与测试骨架（60 条测试、文档模板、交付说明、状态清单）
- 依赖问题诊断和修复（Vite 降级、tsconfig 调整这类工作它能自己搞定）

**它没有替代掉的工作：**
- **产品判断**：什么时候该停，什么时候只是"又多做了一点"——SOLO 不会自然停下来
- **真正的验收**：它会说"全绿""已修完"，但多次出现源码包、文档、版本号和实际不完全一致的情况
- **发布/交付把关**：旧 zip 混进源码包、文档版本号漂移、截图没落地但文档先写了——这些都需要人盯

**提效估算：**

如果由单人纯手工完成到当前 v0.1.19 的程度（含 9 个组件、60 条测试、持久化、导入导出、UIContext 重构），保守估计需要 **2–4 周的集中开发与验证时间**。

在明确需求和分阶段目标下，SOLO 在代码实现与重构层面的吞吐，至少替我承担了 **60%–80% 的机械实现工作量**。

但如果把"写代码 + 验证 + 交付收口"一起算，整体效率提升更接近 **1.5×–2.5×**，而不是无脑 5× 或 10×——因为验收、纠偏、复核、收口仍然要花不少时间。

**可复用的方法：**
- 先做竞品调研再动手写代码，避免重复造轮子
- 不要盲目信任 AI 的"已完成"声明，每一步都要自己验证
- 遇到疑难问题时，让另一个 LLM 帮你审阅 AI 的输出，效果很好
- 诚实标注 mock/未实现功能，比过度承诺更有说服力
- SOLO 适合"先做出来，再一轮轮收紧"的开发节奏，但 stop rule 要人来定

**一句话总结：**
> GrapePaper 证明了"学术论文编辑器不必长得像学术论文"——通过自然视觉隐喻，写作体验可以更温暖、更友好、更有趣。SOLO 不是"一键做完项目"的工具，而是一个能把大量机械工程工作前置消化、再由人来做方向判断和最终验收的协作型开发代理。
